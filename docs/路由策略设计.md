# 路由策略设计文档

## 概述

本文档描述了 pan-api 项目的双层路由机制设计，包括服务商路由和 Token 路由两个维度，以及各种路由策略和组合方案。

## 架构概览

```
用户请求 Model
    ↓
【第一层：服务商路由】Model → VendorModel
    ↓
【第二层：Token路由】VendorModel → VendorToken
    ↓
调用下游服务商
```

## 一、服务商路由策略 (Model → VendorModel)

### 1.1 基础策略

| 策略 | 描述 | 适用场景 |
|------|------|----------|
| **轮询** | 按顺序依次选择，循环使用 | 各服务商性能相近，简单均衡 |
| **权重** | 按配置权重比例分配流量 | 需要按能力分配流量（如 70% A, 30% B） |
| **随机** | 完全随机选择 | 简单场景，无特殊要求 |

### 1.2 考虑因素（过滤/排序条件）

| 因素 | 说明 | 数据来源 |
|------|------|----------|
| **响应时间** | 服务商平均响应延迟 | 历史统计数据 |
| **价格** | 单次请求成本 | PricingItem 配置 |
| **成功率** | 请求成功百分比 | 历史统计数据 |
| **可用性/健康状态** | 服务商是否可用 | 健康检查结果 |
| **负载情况** | 当前并发请求数 | 实时监控数据 |
| **配额限制** | 剩余可用配额 | 服务商API限制 |

### 1.3 组合策略

#### 策略 A: 轮询 + 响应时间过滤
```
1. 获取所有启用的 VendorModel
2. 过滤掉响应时间超过阈值的
3. 在剩余的候选中轮询选择
```
**适用**: 要求低延迟，但不想完全依赖某个服务商

#### 策略 B: 权重 + 价格优先
```
1. 获取所有启用的 VendorModel
2. 按价格排序，优先选择便宜的
3. 同价格区间内按权重分配
```
**适用**: 成本敏感场景

#### 策略 C: 成功率优先 + 负载均衡
```
1. 获取所有启用的 VendorModel
2. 过滤掉成功率低于阈值的
3. 在剩余候选中按成功率加权随机
```
**适用**: 要求高可靠性

#### 策略 D: 自适应策略
```
1. 综合评分 = w1*响应时间 + w2*价格 + w3*成功率 + w4*负载
2. 选择评分最高的
3. 定期动态调整权重
```
**适用**: 复杂场景，需要综合考虑多个因素

#### 策略 E: 健康优先 + 权重
```
1. 获取所有启用的 VendorModel
2. 过滤掉不健康的（熔断状态）
3. 在健康的候选中按权重分配
```
**适用**: 生产环境，保证可用性

## 二、Token路由策略 (VendorModel → VendorToken)

### 2.1 基础策略

| 策略 | 描述 | 适用场景 |
|------|------|----------|
| **轮询** | 按顺序依次选择 | 简单均衡 |
| **权重** | 按权重比例分配 | 不同token能力不同 |
| **随机** | 完全随机 | 简单场景 |

### 2.2 考虑因素（过滤/排序条件）

| 因素 | 说明 | 数据来源 |
|------|------|----------|
| **配额/速率限制** | RPM/TPM 限制 | 服务商API限制 + 实时统计 |
| **响应时间** | 该token平均响应 | 历史统计数据 |
| **成功率** | 该token请求成功率 | 历史统计数据 |
| **Token有效期** | 是否过期 | VendorToken.expiresAt |
| **Token状态** | 是否激活 | VendorToken.isActive |
| **当前并发数** | 该token正在处理的请求数 | 实时计数器 |

### 2.3 组合策略

#### 策略 A: 轮询 + 配额监控
```
1. 获取所有激活且未过期的 Token
2. 过滤掉达到配额限制的
3. 在剩余候选中轮询选择
```
**适用**: 简单均衡，避免超限

#### 策略 B: 权重 + 响应时间
```
1. 获取所有激活且未过期的 Token
2. 按响应时间排序，优先选择快的
3. 同响应时间区间内按权重分配
```
**适用**: 追求低延迟

#### 策略 C: 配额优先 + 轮询
```
1. 获取所有激活且未过期的 Token
2. 按剩余配额比例分配权重
3. 根据动态权重轮询
```
**适用**: 最大化利用配额

#### 策略 D: 负载均衡 + 熔断
```
1. 获取所有激活且未过期的 Token
2. 过滤掉熔断状态的
3. 选择当前并发数最少的
```
**适用**: 高并发场景，避免单个token过载

#### 策略 E: 健康度评分
```
1. 获取所有激活且未过期的 Token
2. 计算健康度评分 = w1*成功率 + w2*剩余配额 + w3*响应时间
3. 选择评分最高的
```
**适用**: 综合考虑多个因素

## 三、双层路由策略组合

### 3.1 典型组合场景

| 场景 | 服务商路由 | Token路由 | 说明 |
|------|-----------|-----------|------|
| **成本优先** | 权重 + 价格优先 | 配额优先 + 轮询 | 优先用便宜的，充分利用配额 |
| **性能优先** | 轮询 + 响应时间过滤 | 权重 + 响应时间 | 追求最快响应 |
| **可靠性优先** | 成功率优先 + 负载均衡 | 负载均衡 + 熔断 | 保证高可用 |
| **均衡模式** | 权重 + 健康优先 | 轮询 + 配额监控 | 综合考虑 |
| **自适应模式** | 自适应策略 | 健康度评分 | 动态调整 |

### 3.2 路由决策流程

```
┌─────────────────────────────────────────────────────────┐
│  用户请求 Model                                           │
└─────────────────────────────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│  【第一层：服务商路由】                                   │
│  1. 获取 Model 对应的所有 ModelBinding                   │
│  2. 应用服务商路由策略                                    │
│     - 过滤：健康状态、响应时间阈值、成功率阈值等           │
│     - 排序/选择：轮询/权重/评分等                         │
│  3. 选定 VendorModel                                    │
└─────────────────────────────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│  【第二层：Token路由】                                    │
│  1. 获取 VendorModel 对应的 VendorToken 列表             │
│  2. 应用 Token 路由策略                                  │
│     - 过滤：激活状态、有效期、配额限制、熔断状态等         │
│     - 排序/选择：轮询/权重/评分等                         │
│  3. 选定 VendorToken                                    │
└─────────────────────────────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│  调用下游服务商                                           │
└─────────────────────────────────────────────────────────┘
```

## 四、数据库设计

### 4.1 ModelBinding 表扩展

```sql
ALTER TABLE `model_binding` 
ADD COLUMN `weight` INT NOT NULL DEFAULT 100 COMMENT '路由权重，值越大分配越多流量' AFTER `is_active`,
ADD COLUMN `strategy` VARCHAR(50) DEFAULT 'WEIGHTED' COMMENT '服务商路由策略' AFTER `weight`;
```

### 4.2 VendorToken 表扩展

```sql
ALTER TABLE `ven_vendor_token` 
ADD COLUMN `weight` INT NOT NULL DEFAULT 100 COMMENT 'Token路由权重' AFTER `is_active`,
ADD COLUMN `rpm_limit` INT COMMENT 'RPM限制' AFTER `weight`,
ADD COLUMN `tpm_limit` INT COMMENT 'TPM限制' AFTER `rpm_limit`;
```

### 4.3 路由统计表

```sql
CREATE TABLE `routing_metrics` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `model_id` BIGINT NOT NULL COMMENT '模型ID',
  `ven_model_id` BIGINT NOT NULL COMMENT '服务商模型ID',
  `vendor_token_id` BIGINT COMMENT '服务商Token ID',
  `strategy` VARCHAR(50) NOT NULL COMMENT '路由策略',
  `request_count` BIGINT NOT NULL DEFAULT 0 COMMENT '请求次数',
  `success_count` BIGINT NOT NULL DEFAULT 0 COMMENT '成功次数',
  `failure_count` BIGINT NOT NULL DEFAULT 0 COMMENT '失败次数',
  `avg_latency_ms` INT COMMENT '平均延迟(毫秒)',
  `total_tokens` BIGINT COMMENT '总token数',
  `last_used_at` DATETIME COMMENT '最后使用时间',
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_model_ven_model_token` (`model_id`, `ven_model_id`, `vendor_token_id`),
  KEY `idx_model` (`model_id`),
  KEY `idx_ven_model` (`ven_model_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='路由统计表';
```

## 五、配置设计

### 5.1 配置示例

```yaml
router:
  # 全局默认策略
  default:
    vendor-strategy: WEIGHTED
    token-strategy: ROUND_ROBIN

  # 服务商路由策略配置
  vendor-strategies:
    weighted:
      enabled: true
      health-check-enabled: true
      response-time-threshold: 5000ms
      success-rate-threshold: 0.95

    round-robin:
      enabled: true
      health-check-enabled: true

    least-cost:
      enabled: true
      consider-response-time: true

  # Token路由策略配置
  token-strategies:
    round-robin:
      enabled: true
      quota-monitoring: true

    weighted:
      enabled: true
      dynamic-weight: true  # 基于配额动态调整权重

    load-balanced:
      enabled: true
      circuit-breaker: true
      max-concurrent-per-token: 10

  # 健康检查配置
  health-check:
    enabled: true
    interval: 30s
    timeout: 5s
    failure-threshold: 3
    success-threshold: 2

  # 熔断器配置
  circuit-breaker:
    enabled: true
    failure-threshold: 5
    timeout: 60s
    half-open-max-calls: 3
```

## 八、实施建议

### 8.1 分阶段实施

#### 第一阶段：基础策略
- 实现轮询、权重、随机三种基础策略
- 实现服务商路由和Token路由的基础功能
- 添加基本的监控统计

#### 第二阶段：健康检查和熔断
- 实现健康检查机制
- 实现熔断器
- 添加响应时间、成功率等过滤条件

#### 第三阶段：高级策略
- 实现自适应路由策略
- 实现配额监控和动态权重调整
- 完善监控和告警

### 8.2 向后兼容

- 默认策略保持随机行为（与现有实现一致）
- 通过配置逐步切换到新策略
- 数据库字段添加默认值

### 8.3 测试策略

- 单元测试：每个路由策略独立测试
- 集成测试：端到端流程测试
- 压力测试：高并发场景验证
- 故障测试：熔断和降级验证

## 九、总结

### 路由策略矩阵

| 维度 | 基础策略 | 过滤条件 | 组合策略 |
|------|----------|----------|----------|
| **服务商路由** | 轮询、权重、随机 | 响应时间、价格、成功率、健康状态、负载、配额 | 5种组合策略 |
| **Token路由** | 轮询、权重、随机 | 配额、响应时间、成功率、有效期、状态、并发数 | 5种组合策略 |

### 关键设计点

1. **双层解耦**: 服务商路由和Token路由独立配置
2. **灵活组合**: 基础策略 + 过滤条件 = 组合策略
3. **可扩展**: 易于添加新的策略和过滤条件
4. **可观测**: 需要监控和统计支持决策
5. **容错机制**: 健康检查 + 熔断降级
